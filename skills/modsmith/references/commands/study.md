# study — map an existing mod

Goal: a document that lets someone (the user, or you in a later session) understand how the mod works without re-reading all the code. Optional argument restricts the scope: `study networking`, `study entities`, `study src/main/java/.../block`.

## Procedure

1. Read the profile. Run `node <skill>/scripts/scan.mjs <mod-root> --inventory` for a quick file inventory (counts, packages, mixins, resources) to plan the reading.
2. Start from the entry points and follow the wiring, rather than reading files alphabetically:
   - Main mod class (`@Mod`, `ModInitializer`), client entry (`@Mod(dist = Dist.CLIENT)`, `ClientModInitializer`, client setup events).
   - Registries: every `DeferredRegister` / `Registry.register` — list what the mod adds.
   - Event subscribers (`@EventBusSubscriber`, `NeoForge.EVENT_BUS.register`, Fabric callbacks) — what game behaviour the mod hooks.
   - Networking: payload types, direction, handlers, what the server trusts.
   - Persistence: NBT/codecs on block entities/entities, data components, attachments, SavedData, config files.
   - Mixins: target, injection type, why it exists.
   - Client: renderers, screens, models, keybinds, particles.
   - Resources: `assets/<modid>/` (lang, models, textures, blockstates), `data/<modid>/` (recipes, loot tables, tags, worldgen), datagen providers.
   Reading order when context is tight: wiring first, then server-side logic and persisted data in full, then client/compat code only skimmed. For mods above ~10k lines, study area by area and merge.
3. Trace 1–3 key gameplay flows end to end (e.g. "player right-clicks cow → ... → item drops"). These are what make the document useful.
4. Note anything surprising or suspicious in a short "Observations" section — but don't do a full audit; point to `audit` instead.

## Output: `STUDY.md` in the modsmith directory

```markdown
# <Mod name> — Study
_Generated by modsmith study on <date>, commit <short sha>. Scope: <all | area>._

## Overview
What the mod does, in 3–5 sentences, from a player's point of view.

## Architecture
Package map (one line per package: responsibility). Entry points and load order.

## Content registered
Tables: blocks, items, entities, block entities, menus, recipes types, data components, attachments, sounds, etc. (only the ones that exist).

## Key flows
Numbered walk-throughs with file:line references.

## Client / server split
What runs where; how client-only code is isolated.

## Networking & persistence
Payloads (direction, fields, handler, validation). What is saved and where (keys!).

## Mixins
| Mixin | Target | Injection | Purpose |

## Dependencies & compatibility
Required/optional mods, integrations.

## Observations
Short list of things worth auditing. No severities here. Phrase possibly-intentional behaviour as a question ("are X and Y meant to share parents?"), not as a bug.
```

For beginners, add a short "How to read this mod" paragraph at the top and explain the terms used. Keep the document factual: every claim should be traceable to a file.
